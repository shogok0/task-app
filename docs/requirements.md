# 課題管理アプリ 要件定義書

## 1. 目的

学生、先生、クラス、チームが課題と締切を正確に管理し、提出忘れを減らすための課題管理アプリを提供する。

本アプリは、個人の TODO 管理ではなく、学校・塾・学習チームなどで発生する「課題の共有」「締切確認」「提出状態の管理」「通知」を扱うことを目的とする。

## 2. 背景と課題

学習現場では、課題情報が口頭、紙、チャット、学習管理システムなどに分散しやすい。結果として、学生は締切を見落とし、先生は誰が課題を確認・提出したか把握しづらくなる。

解決すべき課題:

- 課題の登録場所が分散している
- 締切が近い課題に気づきにくい
- 個人課題とクラス課題が混在して管理しづらい
- 提出済みかどうかを学生自身が把握しにくい
- 先生や管理者がチーム内の課題を安全に共有したい
- 通知が不十分で提出忘れが起きる

## 3. 想定ユーザー

| ユーザー | 説明 | 主な目的 |
| --- | --- | --- |
| 学生 | 課題を受け取り、締切までに提出する利用者 | 課題確認、提出状態管理、通知受信 |
| 先生 | クラスやチームに課題を配布する利用者 | 課題作成、共有、提出状況確認 |
| 管理者 | 組織やチーム設定を管理する利用者 | メンバー管理、権限管理、設定 |

## 4. 利用シーン

- 学生が今日やるべき課題をスマホで確認する
- 学生が課題を提出済みに変更する
- 先生がクラス全体に課題を配布する
- 先生が課題の締切を変更する
- 学生が締切前にメールまたはプッシュ通知を受け取る
- 学生がカレンダーで今月の課題量を確認する
- 先生がクラスメンバーを招待する

## 5. プロダクト方針

本アプリは以下を重視する。

- スマホで毎日使えること
- 締切順に迷わず課題を確認できること
- 権限ミスで他人のデータが見えないこと
- 通知が二重送信されないこと
- 小さく始めて、チーム機能、PWA、リアルタイム更新へ拡張できること

## 6. スコープ

### 6.1 MVPスコープ

MVPでは以下を対象とする。

- ユーザー登録・ログイン
- 個人課題の作成、編集、削除、提出状態変更
- クラス作成、参加、退出
- クラス課題の作成、閲覧、提出状態変更
- 締切順一覧
- カレンダー表示
- 通知設定
- 締切リマインダー送信
- 最低限のPWA対応

### 6.2 MVPでは扱わない範囲

- 成績管理
- ファイル提出
- 採点
- チャット
- 複雑なワークフロー承認
- オフライン編集と自動同期
- ネイティブアプリ
- 複数学校をまたぐ大規模組織管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| NFR-SEC-001 | 認証が必要な画面は未ログインで閲覧できない | Must |
| NFR-SEC-002 | 他ユーザーの個人課題を閲覧・変更できない | Must |
| NFR-SEC-003 | クラス課題は所属メンバーのみ閲覧できる | Must |
| NFR-SEC-004 | 権限はUIだけでなくサーバーとDBでも検証する | Must |
| NFR-SEC-005 | 秘密鍵やサービスロールキーをブラウザに公開しない | Must |
| NFR-SEC-006 | CSRF、XSS、SQL Injectionを防ぐ | Must |

| NFR-OPS-003 | DB migrationを履歴管理できる | Must |

## 9. データ保持方針

- ユーザー削除時の課題データは論理削除を基本とする
- クラス削除は即時物理削除ではなく、アーカイブを優先する
- 通知履歴は二重送信防止と監査のため一定期間保持する
- 個人情報は必要最小限にする

## 10. 成功指標

| 指標 | 目標 |
| --- | --- |
| 初回登録から課題作成までの完了率 | 70%以上 |
| 週次アクティブ率 | 40%以上 |
| 締切通知の送信成功率 | 99%以上 |
| 主要導線のE2Eテスト成功率 | 100% |
| 権限関連の重大インシデント | 0件 |

## 11. 前提条件

- Webアプリとして提供する
- 初期ターゲットはスマートフォン利用を重視する
- 認証、DB、ホスティングはマネージドサービスを活用する
- 初期リリースでは日本語UIを前提とする
