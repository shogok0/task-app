# 技術スタック方針・ベストプラクティス

## 目的

課題管理アプリをゼロから新規開発する場合に、開発速度、拡張性、運用性、通知品質、権限制御のしやすさを高い水準で両立する技術スタックを定義する。

## 推奨スタック

### アプリケーション基盤

- フロントエンド兼BFF: `Next.js App Router`
- UI: `React 19`
- 言語: `TypeScript`
- パッケージマネージャ: `pnpm`
- ランタイム: `Node.js 24 Active LTS`

### UI / フロントエンド

- スタイリング: `Tailwind CSS`
- UIコンポーネント方針: 業務UIに最適化した自前コンポーネントを中心に構築
- フォーム処理: React 19 / Next.js の `Server Actions`
- クライアント状態: 必要最小限の `useState` と `useTransition`
- サーバー状態: 基本は Server Components で取得し、必要に応じて `TanStack Query`

### バックエンド / API

- Webアプリ内バックエンド: `Route Handlers` + `Server Actions`
- バリデーション: `Zod`
- ORM: `Drizzle ORM`

### データ / インフラ

- 主DB: `PostgreSQL`
- BaaS: `Supabase`
  - Postgres
  - Storage
  - Realtime
  - Row Level Security
- 認証 / 組織管理: `Clerk`
- メール通知: `Resend`
- 非同期ジョブ / スケジュール実行: `Upstash QStash`
- デプロイ: `Vercel`

### 品質 / 運用

- E2Eテスト: `Playwright`
- UIテスト: `React Testing Library`
- 整形 / Lint: `Biome`
- 可観測性: `OpenTelemetry`

## この構成を採用する理由

### 1. Webファーストで最短距離を取れる

課題管理は、まずブラウザからすぐ使えることが重要である。Next.js の App Router は、SSR、Server Components、Route Handlers、PWA 導線を一体で扱いやすく、初期開発と運用開始が速い。

### 2. ドメインが強いリレーショナル構造を持つ

本アプリは以下のような関係データが中心になる。

- ユーザー
- 組織
- クラス / チーム
- メンバーシップ
- 課題
- 通知設定
- 通知配信履歴
- 提出状態

このため、NoSQL よりも PostgreSQL が自然であり、検索性・整合性・権限制御でも優位性が高い。

### 3. 権限を DB レイヤーでも守れる

組織・クラス共有機能では、アプリ側のバグだけでデータ漏えいが起きない設計が重要である。Supabase の RLS を使うことで、ユーザー種別や所属に応じたデータ制御を DB 側にも持たせやすい。

### 4. 認証と組織管理を自作しなくてよい

認証は作れてしまうが、運用・保守・例外系で失敗しやすい。Clerk を使うことで、サインイン、セッション管理、組織、ロール、招待などを安定して導入できる。

### 5. 通知を同期処理に載せない

締切通知、再送、時刻差、失敗リトライはすべて非同期に分離した方が安全である。QStash でスケジュール実行と再試行を持ち、Resend でメール配信する構成が扱いやすい。

## ベストプラクティス

### アーキテクチャ

- Web モノリスとして開始し、早い段階で不要なマイクロサービス分割をしない。
- 画面、API、認証、通知を一つのプロダクト責務として管理する。
- ビジネスルールは UI コンポーネントの中に散らさず、アプリケーションサービス層に寄せる。

### フロントエンド

- 一覧・詳細・作成・編集の主要画面は Server Components を基本とする。
- フォーム送信は可能な限り Server Actions を使い、プログレッシブエンハンスメントを保つ。
- クライアントでしか成立しない処理だけを Client Component に閉じ込める。
- カレンダー、通知許可、リッチなインタラクションだけを限定的にクライアント実装する。

### データベース

- すべての主要テーブルに主キー、監査用日時、論理削除方針の有無を明示する。
- クラスや組織の境界を越えたデータ参照を防ぐため、組織スコープ列を明示する。
- 添付ファイル本体は DB に入れず、Storage に保存してメタデータのみ DB で持つ。
- 通知は配信履歴を残し、同一通知の重複送信を防止する。

### 権限

- `member`, `admin` などの役割を明文化する。
- UI 表示制御だけではなく、API と DB の両方で権限をチェックする。
- クラス参加コードや招待リンクは短命かつ失効可能にする。

### 通知

- 通知許可は初回表示直後に求めない。
- 通知はユーザー操作後に価値が伝わった段階で許可を求める。
- メール通知と Web Push は役割を分ける。
  - Web Push: 直近の締切や即時変化
  - メール: 取りこぼし防止、日次 / 週次サマリー
- 配信失敗は再試行可能にし、結果を履歴に残す。

### 品質保証

- 最重要導線は E2E テストで保証する。
- E2E で最低限カバーする導線:
  - 新規登録
  - ログイン
  - 課題作成
  - 課題編集
  - 提出済み切替
  - クラス作成
  - クラス参加
  - 通知設定変更
- UIテストは複雑な表示分岐と入力バリデーションに絞る。

### 運用

- 監視は後付けにしない。
- リクエスト、ジョブ、通知、DB エラーを追跡できるようにする。
- 管理者向けに、ジョブ失敗、配信失敗、RLS 想定外挙動を確認できる運用導線を持つ。

## 採用しない方がよい方針

- 認証のフルスクラッチ実装
- 初期段階からのネイティブアプリ同時開発
- 役割や所属の概念を持たない単純 ToDo 設計
- 通知をアプリ本体の同期HTTP処理で直接送る設計
- 権限制御をフロントエンドだけに任せる設計
