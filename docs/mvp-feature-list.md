# 課題管理アプリ MVP機能一覧

## 1. 目的

この文書は、課題管理アプリの初期リリースで実装する機能と、MVP後に回す機能を明確にする。

MVPの目的は、ユーザーが「課題を登録し、締切を確認し、提出済みにし、通知を受け取る」体験を最短で成立させること。

## 2. MVPの成功条件

MVPは以下を満たせば成功とする。

- ユーザーが登録・ログインできる
- 個人課題を作成、編集、削除できる
- クラスを作成し、招待コードで参加できる
- クラス課題を作成・閲覧できる
- 課題を締切順に確認できる
- 課題を提出済みにできる
- 締切前に通知を受け取れる
- スマホで主要操作が問題なく使える
- 権限外の課題を閲覧・編集できない

## 3. リリース段階

| 段階 | 目的 | 内容 |
| --- | --- | --- |
| MVP 0 | 土台構築 | 認証、DB、基本レイアウト、デプロイ |
| MVP 1 | 個人課題管理 | 個人課題CRUD、締切順一覧、提出状態 |
| MVP 2 | クラス共有 | クラス作成、参加、クラス課題 |
| MVP 3 | 通知・PWA | 締切通知、PWA基本対応、監視 |

## 7. MVP 3: 通知・PWA・運用

| ID | 機能 | 説明 | 優先度 | 完了条件 |
| --- | --- | --- | --- | --- |
| MVP3-001 | 通知設定 | 通知の有効化、何日前、時刻を設定する | Must | 設定がユーザーごとに保存される |

| MVP3-005 | PWA manifest | ホーム画面追加に必要なmanifestを用意する | Must | Lighthouseでinstallable条件を満たす |

## 8. MVPで実装しない機能

| 機能 | 理由 |
| --- | --- |
| ファイル提出 | ストレージ、権限、容量管理が必要で初期範囲が広がる |
| 採点 | 課題提出後の運用設計が必要 |
| コメント | 通知とモデレーションの設計が増える |
| Web Push | 初期はメール通知で価値検証し、次フェーズで追加する |
| リアルタイム共同編集 | 課題管理の初期価値に直結しない |
| 管理者向け分析画面 | 利用データが溜まってから設計する |
| ネイティブアプリ | PWAでまず検証する |
| 複雑なオフライン同期 | データ競合解決が必要で初期には重い |

## 9. 優先順位

### P0: 必ず実装

- 認証
- 個人課題CRUD
- 提出状態変更
- 締切順一覧
- クラス作成・参加
- クラス課題
- 基本的な権限チェック
- 通知設定
- メール通知
- E2Eテスト

### P1: 早期に実装

- カレンダー表示
- PWA manifest
- 通知失敗監視
- 課題絞り込み
- クラス退出
- パスワード再設定

### P2: 利用状況を見て実装

- Web Push
- Supabase Realtime
- メンバーロール変更
- クラスアーカイブ
- ファイル添付
- コメント
- 管理画面

## 10. MVP受け入れテスト

| シナリオ | 期待結果 |
| --- | --- |
| 新規ユーザーが登録する | ログイン状態になり、ダッシュボードが表示される |
| 個人課題を作成する | 締切順一覧とカレンダーに表示される |
| 課題を提出済みにする | 未提出一覧から消え、提出済みとして表示される |
| クラスを作成する | 招待コードが発行される |
| 別ユーザーが招待コードで参加する | クラス詳細とクラス課題が見える |
| studentがクラス課題を編集しようとする | 操作できない |
| teacherがクラス課題を作成する | クラスメンバーに表示される |
| cronが通知処理を実行する | 対象ユーザーにメールが送信される |
| cronを再実行する | 同一通知が二重送信されない |
| 未ログインで保護画面へアクセスする | ログイン画面へ誘導される |

## 11. MVPリリース判定

以下をすべて満たしたらMVPリリース可能とする。

- `typecheck` が通る
- `lint` が通る
- 単体テストが通る
- 主要導線のE2Eテストが通る
- RLS policyのテストが通る
- Production deployが成功する
- 通知cronの手動実行が成功する
- 主要画面がスマホ幅で崩れない
- 利用規約とプライバシーポリシーを表示できる
